# Base PRP Template v3 — XML Structure for Native Execution

The canonical PRP structure consumed by `/KGP:prp-execute`. Generated by `/KGP:prp-create` via the `software-architect` skill; validated by `/KGP:prp-validate`.

## Core Principles

1. **Context is King**: Include ALL necessary documentation, examples, and caveats
2. **Validation Loops**: Provide executable tests/lints the executor can run and fix
3. **XML for Machine Parsing**: Every task, criterion, and decision is a structured element
4. **Intent Anchors**: The executor disambiguates against locked intent, not guesses
5. **Design-First UI**: User-facing PRPs start with a Design Foundation phase
6. **Global rules**: Follow all rules in the project's CLAUDE.md

---

```xml
<prp name="[feature-name]" version="1.0">

<metadata>
  <created>[YYYY-MM-DD]</created>
  <author>software-architect skill</author>
  <target-branch>main</target-branch>
  <estimated-effort>[S|M|L|XL]</estimated-effort>
  <confidence-score>[1-10]</confidence-score>
</metadata>

<goal>
[Specific, measurable end state. What exists when this PRP is complete?]
</goal>

<intent-anchors>
  <!-- Locked during /KGP:prp-create intent-lock (B1). Executor uses these to
       disambiguate — they are authoritative over any inferred interpretation. -->
  <what>[The deliverable, one sentence]</what>
  <who>[The user / role]</who>
  <why>[The motivating outcome]</why>
  <out-of-scope>
    <item>[Explicitly excluded functionality]</item>
  </out-of-scope>
  <success-signal>[The one observation that proves it works]</success-signal>
</intent-anchors>

<context>
  <business-value>
    [Why this matters. Business impact, user benefit, problems solved.]
  </business-value>

  <decisions>
    <!-- Architectural choices the user already approved (B2). Executor honors
         these as locked — chosen, not assumed. -->
    <decision id="D1">
      <topic>[e.g., library choice, file location, API style]</topic>
      <choice>[The locked choice]</choice>
      <rationale>[Why]</rationale>
    </decision>
  </decisions>

  <prerequisites>
    <prerequisite>[Dependency or setup required before starting]</prerequisite>
  </prerequisites>
</context>

<codebase-analysis>
  <existing-patterns>
    <pattern file="[path/to/file.ts]" usage="[What to copy/follow]"/>
  </existing-patterns>

  <affected-files>
    <file action="modify" path="[src/path/file.ts]" reason="[Why modifying]"/>
    <file action="create" path="[src/path/new-file.ts]" reason="[What it contains]"/>
  </affected-files>

  <dependencies>
    <dependency name="[package-name]" version="[^1.0.0]" purpose="[Why needed]"/>
  </dependencies>

  <gotchas>
    <gotcha>[Known issue or quirk to watch for]</gotcha>
  </gotchas>
</codebase-analysis>

<research-findings>
  <recommended-libraries>
    <library name="[package-name]" purpose="[what problem it solves]">
      <rationale>[Why this over alternatives]</rationale>
      <docs-url>[Link to official documentation]</docs-url>
      <install>[npm install X / pip install X]</install>
    </library>
  </recommended-libraries>

  <patterns-to-follow>
    <pattern source="[URL or 'official docs']">
      <description>[What the pattern accomplishes]</description>
      <applicability>[How it applies to this feature]</applicability>
    </pattern>
  </patterns-to-follow>

  <pitfalls-to-avoid>
    <pitfall source="[URL or community knowledge]">
      <issue>[Common mistake others have made]</issue>
      <mitigation>[How to avoid it here]</mitigation>
    </pitfall>
  </pitfalls-to-avoid>

  <documentation-references>
    <reference url="[URL]" topic="[Topic]">
      <key-points>
        <point>[Critical detail from documentation]</point>
      </key-points>
    </reference>
  </documentation-references>
</research-findings>

<phases>

  <!-- Phase 0 is REQUIRED for user-facing UI PRPs; omit for backend/CLI/data PRPs -->
  <phase id="0" name="Design Foundation">
    <description>Design tokens, component inventory, and design-skill directives before any implementation</description>
    <tasks>
      <task id="0.1" agent="frontend-engineer" effort="S" value="H">
        <description>Establish/confirm design tokens (colors, typography, spacing). Priority: project design system → kgprodesign-branding skill (KGP properties) → synced Claude Design system.</description>
        <acceptance-criteria>
          <criterion>Token source documented; tokens available as CSS variables or theme config</criterion>
        </acceptance-criteria>
      </task>
      <task id="0.2" agent="frontend-engineer" effort="S" value="H">
        <description>Component inventory: list pages/components to build; mark reused vs created. Implementation tasks should invoke the frontend-design skill (if installed) for generation; dataviz for charts.</description>
        <acceptance-criteria>
          <criterion>Inventory table exists in the PRP or a linked doc</criterion>
        </acceptance-criteria>
      </task>
    </tasks>
  </phase>

  <phase id="1" name="Foundation">
    <description>[What this phase accomplishes]</description>
    <tasks>
      <task id="1.1" agent="[agent-type]" effort="[S|M]" value="[H|M|L]" timeout="[default|extended]">
        <description>[Clear, actionable description of what to do]</description>

        <files>
          <file action="[create|modify|delete]">[path/to/file.ts]</file>
        </files>

        <pseudocode>
// Follow pattern from [existing file]
[Pseudocode matching project style]
        </pseudocode>

        <acceptance-criteria>
          <criterion>[Specific, verifiable outcome — executable check preferred]</criterion>
        </acceptance-criteria>

        <handoff>
          <expects>[What this task needs from previous tasks]</expects>
          <produces>[What this task provides to next tasks]</produces>
        </handoff>
      </task>
    </tasks>
  </phase>

  <phase id="2" name="Core Implementation">
    <description>[What this phase accomplishes]</description>
    <tasks><!-- Tasks --></tasks>
  </phase>

  <phase id="3" name="Integration">
    <description>[What this phase accomplishes]</description>
    <tasks><!-- Tasks --></tasks>
  </phase>

  <phase id="4" name="Testing & Validation">
    <description>[What this phase accomplishes]</description>
    <tasks><!-- Test implementation tasks --></tasks>
  </phase>

</phases>

<validation>
  <level name="syntax" run-after="each-task">
    <command>[lint command for this project]</command>
    <command>[typecheck command for this project]</command>
  </level>

  <level name="unit" run-after="phase">
    <command>[unit test command]</command>
  </level>

  <level name="integration" run-after="all">
    <command>[integration test command]</command>
    <command>[build command]</command>
  </level>
</validation>

<success-criteria>
  <criterion priority="P0">[Must be true for completion]</criterion>
  <!-- verify="adversarial": executor spawns an independent qa-engineer verifier
       prompted to REFUTE the claim. Use for security/payments/data-integrity. -->
  <criterion priority="P0" verify="adversarial">[Security-critical claim]</criterion>
  <!-- verify="visual": executor runs the screenshot-critique-refine loop
       (ui-visual-testing skill) on every changed page/view. -->
  <criterion priority="P0" verify="visual">[Every changed page passed one visual QA iteration against the style guide]</criterion>
  <criterion priority="P1">[Should be true]</criterion>
</success-criteria>

<anti-patterns>
  <avoid>[Pattern to avoid during implementation]</avoid>
</anti-patterns>

</prp>
```

## Agent Types Reference

| Agent | Use For |
|-------|---------|
| backend-engineer | API, services, business logic, auth |
| frontend-engineer | UI, components, state, styling |
| data-engineer | Schema, migrations, queries |
| qa-engineer | Tests, security review, adversarial verification |
| devops-engineer | CI/CD, infrastructure |
| document-specialist | Documentation |

## Effort Sizing Reference

Only S and M tasks are allowed in a PRP — decompose L/XL before inclusion.

| Size | Time | Complexity |
|------|------|------------|
| S | < 15 min | Single file, clear pattern |
| M | 15-30 min | 2-3 files, some decisions |

## Value Ranking Reference

| Value | Meaning |
|-------|---------|
| H | Core functionality, blocking, user-facing |
| M | Important, not blocking, enhances experience |
| L | Nice to have, polish, optimization |

## Timeout Reference

| Timeout | When to Use |
|---------|-------------|
| default | Standard tasks (300s) |
| extended | Test suites, E2E, builds, migrations, large codebases (600s) |
