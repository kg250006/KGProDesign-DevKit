# Site addresses, custom domains, and certificates

How a KGP Host site gets its address and HTTPS certificate, how custom domains are added, and how the
platform's wildcard certificate is renewed and checked. Design: ADR 0007 in the KGP-WebHosting-Tools repo;
the owner's step-by-step runbook is `docs/runbooks/wildcard-certificate.md` there.

## Which addressing an instance uses

`kgp instance show --json --yes` shows the instance settings:

| Key | Values | Meaning |
|---|---|---|
| `site_addressing` | `subdomain` (default), `wildcard` | `wildcard`: every `SITE.PLATFORM_DOMAIN` is served through one cPanel subdomain, `*.PLATFORM_DOMAIN`. `subdomain`: each site gets its own cPanel subdomain. |
| `dns_authority` | `cpanel` (default), `external` | `external`: the platform domain's public DNS is not the zone cPanel edits. Doctor then skips `zone_sync` and `write_test` and checks `acme_alias` instead. |
| `[acme] challenge_alias`, `dir` | a host name in a zone cPanel controls; default dir `kgp-acme` | Where the wildcard certificate's DNS challenge records go, and the server folder for the renewal. |

sitepage.app uses `wildcard` and `external`.

## Sites on the wildcard

- `kgp sites create SITE --json --yes` (owner only) registers the site with the agent and makes **no cPanel
  call**: the site answers on `https://SITE.PLATFORM_DOMAIN` within seconds, already covered by the wildcard
  certificate. It refuses (exit 7 `wildcard_missing`) until the owner has run `kgp server wildcard`.
- The platform folder's `.htaccess` (generated by `kgp server wildcard`, never edited by hand) sends
  `SITE.PLATFORM_DOMAIN` into the site's folder; the site's own rules take over from there.
- A name with no site (a typo, a deleted site, `branch--site` previews, which do not exist yet) answers **404 with
  the "Nothing lives here." page**, `X-KGP-No-Site: 1` and `X-Robots-Tag: noindex`. On a site that should exist
  this means its folder has no rules yet: deploy it (`kgp deploy --prod`, when asked), or the owner runs
  `kgp server upgrade`, which re-renders every site's rules.
- Names two levels deep (`a.b.PLATFORM_DOMAIN`) have no valid certificate: a wildcard covers one label.
- Sites created before the wildcard may still have their own cPanel subdomain. It wins over the wildcard and is
  harmless; removing it is an owner decision made in cPanel.
- `kgp sites delete SITE --yes` removes the site; its address then shows the no-site page. With wildcard
  addressing only a legacy subdomain that points at the site's own folder is removed from cPanel.

## Custom domains

A client domain always needs one cPanel entry. A CNAME alone cannot work: the server IP is shared, so the web
server needs a cPanel entry to send the name to this account, and a certificate can only be installed for a
domain on the account.

1. The owner asks; you run `kgp domains add DOMAIN --json --yes` (add `--primary` to make it the main address;
   every other address then 301s to it). It creates a cPanel addon domain (or a subdomain when DOMAIN is under a
   domain of the account) pointing at the site folder, adds the name to the site's host allowlist, requests
   AutoSSL, and prints the DNS records in `dns.records` / `instructions_md`.
2. Give those records to the domain owner. Typical: `www` CNAME to `SITE.PLATFORM_DOMAIN`; the bare domain an A
   record to the server IP that the command prints (or the DNS provider's ALIAS/flattening). Never change DNS
   yourself.
3. `kgp domains status DOMAIN --json --yes` shows `dns` (`ok` or `waiting for customer DNS`) and the certificate
   state. AutoSSL issues the domain's own certificate once DNS reaches the server, usually within minutes.
4. `kgp domains remove DOMAIN --yes --json` (owner only) detaches it and removes its cPanel domain.

Each custom domain uses one cPanel addon-domain slot; sites on the wildcard use none.

## Which certificate covers what

| Name | Certificate | Renewed by |
|---|---|---|
| `SITE.PLATFORM_DOMAIN` (wildcard sites) | Let's Encrypt `*.PLATFORM_DOMAIN` (also lists the apex) | acme.sh in cPanel cron (below) |
| Apex, `www`, `deploy.`, legacy explicit site subdomains | AutoSSL, one per cPanel name | cPanel AutoSSL, automatically |
| Custom domains | AutoSSL for that domain | cPanel AutoSSL, after the client's DNS points at the server |

The wildcard certificate is installed on the `*.PLATFORM_DOMAIN` vhost only; it never replaces an AutoSSL
certificate.

## How the wildcard certificate is issued and renewed

- AutoSSL cannot issue it when the platform domain's public DNS is outside cPanel ("DNS DCV: No local authority").
  Instead Let's Encrypt validates through a **permanent CNAME** in the platform domain's public DNS:
  `_acme-challenge.PLATFORM_DOMAIN CNAME _acme-challenge.CHALLENGE_ALIAS.` The challenge TXT records are written,
  through the cPanel API, into the alias's zone, which cPanel does control. That CNAME must never be removed.
- acme.sh 3.1.6 (pinned by sha256) lives in `~/kgp-acme` on the server (folders 0700, token file 0600), with a
  daily cPanel cron line marked `# kgp-acme`. It renews about 30 days before expiry (certificates last 90 days).
  KGP's own deploy hook installs the new certificate on `*.PLATFORM_DOMAIN` through the cPanel HTTPS API; no key
  or token is ever on a command line, and the token is redacted from the log.
- One-off runs (`kgp server cert run`) add a temporary every-minute cron line (`# kgp-acme-once`) that the CLI
  removes as soon as the run starts; they wait for the next cron minute, so a run takes 1 to 3 minutes.

## Checking it

```sh
kgp server cert status --json --yes        # certificate.days_left, not_after, cron, last_run (exit, mode)
kgp instance doctor --json --yes           # ssl (wildcard required) and acme_alias checks
kgp server cert run --staging --json --yes # safe: Let's Encrypt staging, separate state, nothing installed
```

| Signal | Meaning | Who acts |
|---|---|---|
| `status` exit 7 `certificate_expiring` | wildcard certificate missing or under 7 days | owner: `kgp server cert run`, runbook |
| doctor `ssl` warn | under 14 days left; renewal should have happened by now | read `last_run` and the log; tell the owner |
| doctor `acme_alias` fail | the challenge CNAME is missing, or alias zone writes do not reach its nameservers | owner fixes DNS per the check's `fix` |
| `last_run.exit` not 0 | the last renewal failed; `log_tail` says why | owner |
| every wildcard site shows a certificate error at once | the wildcard certificate expired | owner, urgently |

Failed-run hints in the log: `dns_cpanel` login or zone errors mean the renewal token was revoked (owner creates
one, `kgp login --acme`, `kgp server cert setup`); validation errors mean the CNAME is wrong; `install_ssl failed`
comes from the deploy hook.

## Owner-only (run only on an explicit request)

- `kgp server wildcard` (router, no-site page, `*.PLATFORM_DOMAIN` document root).
- `kgp login --acme` (stores the renewal token; it warns `broader_than_needed` when the host only offers
  full-access tokens, which is expected on some hosts).
- `kgp server cert setup` and any production `kgp server cert run`.
- **Never** run `kgp server cert run --force` against production on your own: Let's Encrypt allows 5 duplicate
  certificates a week. It needs `--yes` and fails with exit 2 `confirmation_required` without it.
- Never touch `~/kgp-acme`, the `# kgp-acme` cron line, or the `_acme-challenge` CNAME directly.
